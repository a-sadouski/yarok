# Надёжность и защита: шаги 3–4

Проверено локально 23 октября 2026 года. Изменения затрагивают `yarok` и соседний `yarok-be`;
обновлять frontend и backend нужно вместе.

| Проблема | Изменение | Проверка |
| --- | --- | --- |
| Неизвестная категория показывала первую | Страница 404; ошибка API не маскируется под пустой каталог | HTTP через production Nuxt |
| Сбой проверки сессии выглядел как неверный пароль | Разделены 401, 429 и недоступность API; форма сохраняется при 401, повторный вход доступен в новой вкладке | Типы, тесты разбора ошибок, HTTP auth/503 |
| Скрытый товар исчезал из админки | Отдельный защищённый список всех товаров, no-store | DB и HTTP через proxy |
| При редактировании терялись свойства вариантов | Сохранение oldPrice и isActive; у простого товара фиксированный серый цвет по бизнес-правилу | Тесты multipart-сериализации и DB |
| Удаление картинки оставалось только в предпросмотре | Явное removeImage; сервер удаляет ссылки в транзакции | DB и HTTP с локальной заглушкой Storage |
| Карта могла зависнуть при недоступном SDK | Общая загрузка с тайм-аутом, повторная попытка и текстовый адрес | Тесты загрузчика |
| Вход не ограничивал перебор | 5 попыток за 15 минут на IP; клиентский X-Forwarded-For заменяется адресом socket | Тесты времени и HTTP с подменёнными заголовками |
| Cookie-запросам записи требовалась защита от CSRF | Обязательный нестандартный заголовок; cookie-авторизация остаётся отдельной проверкой | HTTP с отсутствующим заголовком/сессией |
| Сбой после загрузки мог оставить новый объект Storage | Компенсационное удаление до попытки COMMIT; неопределённый COMMIT не удаляет потенциально действующий объект | Принудительная ошибка DB после загрузки |

Для воспроизведения: `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`,
`node scripts/test-local-integration.mjs`. Последняя команда требует собранного backend,
Docker и локального образа `postgres:16`. Она выполняет 54 backend-проверки, поднимает
одноразовую БД и локальную заглушку Storage, затем удаляет свои процессы и контейнер.
HTTP smoke-тесты backend отдельно запускаются через `yarok-be/scripts/Test-Smoke.ps1`.

## Границы результата

- Production и существующие БД не изменялись. `003_integrity.sql` проверена только на тестовой БД;
  перед ручным применением к существующим данным нужны резервная копия и проверка нарушенных связей.
- Реальные SMTP, Supabase, HTTPS и цепочка production proxy требуют проверки окружения.
  Контракт очистки объектов сверялся с [официальным Storage API](https://supabase.github.io/storage/).
- Лимиты находятся в памяти одного процесса. Для нескольких экземпляров нужен общий limiter
  либо ограничение на доверенном входном proxy.
- Logout удаляет cookie, но подписанный токен остаётся валиден до истечения 12 часов.
  Экстренный отзыв выполняется сменой session secret; отдельного хранилища сессий пока нет.
- Старые объекты после замены/удаления изображений остаются в Storage. Удаляются их ссылки;
  сборка неиспользуемых объектов должна быть отдельной контролируемой операцией.
- Браузерные E2E, аудит доступности и CI относятся к следующим этапам. Эти HTTP-проверки
  не заменяют проверку интерфейса в реальном браузере.
